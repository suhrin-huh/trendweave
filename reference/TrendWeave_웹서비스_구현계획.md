# TrendWeave 웹서비스 구현 계획

작성일: 2026-10-21

## 1. 목표와 우선순위

현재 폴더의 Vue 채팅 화면과 FastAPI 서버를 기반으로, `AI_Agent_설계_trendweave.ipynb`의 패션 트렌드 분석 에이전트를 웹서비스로 이식한다. 사용자는 **예시 질문 버튼을 한 번 클릭하여 실제 분석을 시작하고, 완성된 상품기획 보고서를 읽거나 PDF로 다운로드**할 수 있어야 한다.

`작업내용정리.md`에 따라 먼저 UNIQLO 대상의 **런웨이·컬러·시장·브랜드 4축 전체 조사 → 고정 형식 보고서**를 완성한다. 질문 유형에 따른 분석 축 선택과 동적 보고서 형식은 2차 확장으로 둔다.

이 문서는 로컬 코드와 노트북을 정적으로 분석한 구현 계획이다. 현재 외부 API 호출, 노트북 실행, 패키지 호환성 검증은 수행하지 않았으며, 아래 파일 및 API 설계는 구현 제안이다.

### 주요 차이와 주의점

- 현재 서비스의 도메인은 **운영 장애 대응**이다. 화면 문구만 바꾸거나 기존 장애 분석 프롬프트만 수정해서는 노트북 기능이 구현되지 않는다.
- 기존 `/chat/stream`의 누적 `events` 처리 방식과 달리, 노트북은 병렬 Reducer로 `trace`를 합친다. 기존 SSE 변환을 그대로 복사하면 이벤트 누락·중복이 생길 수 있다.
- 현재 화면은 `{{ item.text }}`로 텍스트를 표시한다. 보고서의 제목·표·목록·참고 링크를 읽기 좋게 표시하려면 Markdown 렌더링이 필요하다.
- 기존 대화 저장소에는 `report_id`, 보고서 구조화 결과, 처리 상태가 없다. PDF 다운로드를 위해 최종 결과를 독립적으로 저장해야 한다.
- 기존 `LLM_BACKEND=fake`는 장애 대응 시연용이다. 이 모드가 패션 웹 검색까지 수행하는 것처럼 표시하지 않도록 설정을 구분한다.

## 3. 노트북에서 우선 이식할 기능

노트북의 마지막 통합 구현을 기준으로 하며, Gradio 화면을 옮기는 대신 분석 함수와 그래프를 모듈로 분리한다.

```text
입력 정규화 → 요청 해석 및 검색 계획
                    ↓
           4개 Research 병렬 실행
           검색 → 문서 평가 → 충분성 판단
                    ↑            ↓
                 검색어 수정   Signal 추출
                    ↓
              전략 작성 ↔ Critic 검토
                    ↓
               Markdown 보고서
```

### 유지할 동작

1. 시즌과 상품기획 요청을 입력받고, 브랜드는 UNIQLO로 고정한다.
2. `RequestProfile`로 타깃 고객·중점 상품군·조건·우선순위를 추출한다.
3. `Send`로 4축을 병렬 실행하고, `research_results`와 `trace`의 Reducer를 유지한다.
4. URL 중복 및 제외 출처를 걸러내고 문서 관련성·시즌 일치를 평가한다. Market·Brand에는 별도의 시즌 판정 규칙을 적용한다.
5. 유효 문서 수와 필수 측면 충족 여부를 코드로 판단하여 검색어를 수정한다.
6. 문서 ID가 연결된 구조화 Signal을 추출하고, 자료 충분도로 신뢰도를 계산한다.
7. 상품기획 방향 3개를 작성하고, 규칙 검사와 LLM Critic을 수행한다.
8. `major` 문제에만 재작성하고, 한도에 도달하면 미해결 문제를 보고서에 명시한다.
9. 최종 Markdown은 코드로 조립한다. PDF 생성 시 LLM을 다시 호출하지 않는다.
10. Planner 실패 시 기본 검색 계획, 축별 실패 시 빈 결과와 낮은 신뢰도, Critic 실패 시 규칙 검사로 진행하는 대체 동작을 유지한다.

노트북 기본 상한은 **축별 검색 총 3회(첫 검색 포함), 최소 유효 문서 3개, 추출 문서 최대 6개, 전략 재작성 최대 2회, 그래프 recursion limit 50**이다. 실제 네트워크 재시도와 검색 루프 횟수는 별도 항목으로 관리한다.

### 실행 환경 분리

- `!pip install`, `IPython.display`, 그래프 이미지 출력, `demo.launch()`, 자동 실행 테스트 셀을 서버 코드에 포함하지 않는다.
- 노트북은 `GOOGLE_API_KEY`, `TAVILY_API_KEY`와 Gemini·Tavily 조합을 사용한다. 1차 구현도 이 조합을 우선하여 모델 변경에 따른 동작 차이를 줄인다.
- 노트북 모델 식별자 `google_genai:gemini-3.1-flash-lite`는 설정 기본값 후보로 옮기되, 구현 첫 단계에서 실제 사용 가능 여부를 확인한다. 계정별 호출 한도와 모델 지원 여부를 노트북 설명만으로 확정하지 않는다.
- 모델 이름·동시 실행 수·호출 속도·timeout·재시도 상한을 환경변수로 분리한다. 모델과 평가 모델은 같은 공급자 한도를 공유할 수 있으므로 공용 제한기를 둔다.
- 노트북의 동기 `invoke`와 `time.sleep`을 FastAPI 이벤트 루프에서 직접 실행하지 않는다. 초기 구현은 제한된 작업 스레드에서 동기 그래프를 실행하고, 진행 이벤트를 안전하게 전달한다. 비동기 전환은 필요할 때 진행한다.

## 4. 사용자 경험

### 4.1 예시 질문 버튼

채팅 입력창 위에 **`예시 질문으로 보고서 생성`** 버튼 하나를 추가한다. 버튼 근처에 예시 질문 전문과 분석 시즌을 표시하여 어떤 분석이 실행되는지 알 수 있게 한다.

기본 예시:

> 2027 S/S 시즌 UNIQLO 상품기획을 위해, 한국의 20~30대 고객이 일상에서 활용하기 쉬운 상품 중심으로 런웨이·컬러·시장·브랜드 트렌드를 분석하고 상품기획 방향 3개를 제안해줘.

- 버튼을 누르면 예시 질문을 사용자 말풍선으로 추가하고 즉시 실제 분석을 시작한다. 입력창에 문장을 채우는 데서 끝나지 않는다.
- 시즌 기본값은 노트북 재현용 `2027 S/S`로 두며 화면에서 수정할 수 있게 한다. 기본 분석일은 실행 시점의 날짜로 계산한다.
- 1차 자유 입력도 같은 분석 API를 사용하며, 항상 4축 상품기획 보고서를 생성한다고 안내한다. 인사·질문 분류와 문맥 기반 후속 질문 처리는 2차 범위로 둔다.
- 별도 클릭 핸들러만 두고 분석 요청 함수는 공통으로 사용한다. 동기식 `sending` 확인과 서버 작업 ID를 통해 중복 클릭을 막는다.

### 4.2 생성 중 표시

`요청 해석 → 4축 조사 → 전략 작성 → 검토·재작성 → 완료`를 표시한다. 조사 단계는 축별 검색 시도와 완료 여부를 보여준다. 아직 산정하지 않은 진행률 숫자는 표시하지 않는다.

노트북은 분석 시간을 약 2~4분으로 안내하지만, 실제 처리 시간은 API 한도와 재검색에 따라 달라진다. UI는 이를 예상 시간으로만 안내한다. 실행 중 버튼을 비활성화하고, 실패 시 원인을 이해할 수 있는 메시지와 재시도 수단을 제공한다.

### 4.3 보고서 표시

채팅 안에는 요약과 완료 상태, `전체 보고서 보기`, `PDF 다운로드`를 담은 보고서 카드를 표시한다. 전체 보고서는 넓은 패널 또는 모달에서 Markdown으로 렌더링한다. 긴 원문을 좁은 말풍선에 모두 펼치지 않아도 읽을 수 있도록 한다.

최종 보고서에는 노트북의 다음 구성을 유지한다.

- Executive Summary, Research Findings, Integrated Analysis
- Strategic Product Directions 3개, Management Considerations
- Data Quality, Review Notes, Agent Trace, References, Report Scope

Data Quality와 미해결 검토 사항을 요약 카드에서도 확인할 수 있게 한다. Markdown 렌더링 시 원시 HTML을 제한하고 정제하여 외부 자료가 실행 가능한 HTML로 삽입되지 않도록 한다.

## 5. 백엔드와 API 설계

### 5.1 작업 생성과 이벤트 구독 분리

보고서 생성은 긴 작업이므로 **POST로 생성하고 작업 ID로 조회·구독**한다. 기존 EventSource의 자동 재연결이 보고서 분석을 다시 실행하지 않도록, GET 이벤트 구독에는 생성 동작을 넣지 않는다.

| API 제안 | 역할 |
|---|---|
| `POST /reports` | 입력 검증, 작업 생성, `202 Accepted`와 `report_id` 반환 |
| `GET /reports/{report_id}` | 상태·단계·최종 Markdown·요약·오류 조회 |
| `GET /reports/{report_id}/events` | 기존 작업의 진행 이벤트를 SSE로 구독 |
| `GET /reports/{report_id}/pdf` | 완료된 동일 보고서를 PDF 파일로 다운로드 |

생성 입력 예:

```json
{
  "season": "2027 S/S",
  "planning_request": "한국의 20-30대 고객이 일상에서 활용하기 쉬운 상품 중심으로 기획해줘.",
  "thread_id": "웹 세션 ID"
}
```

브랜드는 서버에서 UNIQLO로 지정한다. 빈 요청·길이 제한·시즌 표기를 검증한다. 프런트엔드는 동일 출처인 8600 서버만 호출하며, `web_demo_server.py`에서 네 API를 8100으로 중계한다. PDF의 바이너리 본문, 상태 코드, `Content-Type`, `Content-Disposition`도 유지한다.

### 5.2 저장과 실행

- 별도 `report_jobs` 테이블에 입력, `queued/running/completed/failed` 상태, 단계, 생성·완료 시간, 최종 Markdown, JSON 직렬화된 구조화 결과, 오류를 저장한다.
- 작업별 순번을 가진 진행 이벤트를 저장한다. SSE는 이벤트 ID를 전달하고 재연결 시 마지막 ID 이후를 재생하여 누락·중복 표시를 방지한다. 다른 작업·세션의 이벤트가 섞이지 않도록 한다.
- 한 프로세스와 소규모 사용을 전제로 제한된 백그라운드 실행기를 둔다. 공급자 호출 제한에 맞춰 동시 작업을 제한한다. 모델·검색 도구·그래프는 lifespan에서 초기화한다.
- 서버 재시작으로 중단된 작업은 다음 시작 시 실패 처리하고 재시도를 안내한다. 완료된 보고서는 재시작 후에도 조회·PDF 다운로드가 가능하게 한다. 작업 자동 재개와 다중 워커 큐는 후속 범위다.
- SSE에는 연결 유지용 heartbeat를 보내고 프록시가 스트림을 버퍼링하지 않게 한다. 브라우저 연결이 끊겨도 실행 중인 작업을 새로 만들지 않는다.
- 한 축의 검색 실패는 부분 결과로 처리한다. 모든 축의 검색 실패·근거 부재는 정상 완료와 구별하여 실패 또는 자료 부족 상태를 명확히 안내하고, 근거 없는 전략을 성공 결과로 제시하지 않는다.
- 보고서 ID는 예측하기 어려운 값으로 발급한다. 1차는 로컬 데모 범위이며, 공개 서비스 배포 전에는 사용자 인증과 보고서 소유권 검증이 별도로 필요하다.

## 6. PDF 다운로드 설계

**완료된 보고서의 저장된 Markdown → HTML → PDF** 흐름을 사용한다. 웹 표시와 PDF가 같은 결과를 사용하여 재생성에 따른 내용 차이를 방지한다.

1. 서버 측 Markdown 변환과 PDF 전용 HTML 템플릿을 작성한다.
2. HTML 인쇄를 지원하는 PDF 도구 후보로 Playwright의 Chromium을 우선 검증한다. 구현 초기에 설치·실행 가능 여부와 의존성을 확인하여 확정한다.
3. 한국어 글꼴을 로컬 자원으로 제공하고 PDF에 반영한다. 글꼴 라이선스와 배포 가능 여부를 확인하고 출처를 기록한다.
4. A4 여백·페이지 번호·제목·표 헤더 반복·긴 URL 줄바꿈을 설정한다. 짧은 전략 표는 가능한 한 묶고, 페이지보다 긴 표는 나눌 수 있도록 한다.
5. Agent Trace의 접힌 HTML 상세 요소도 PDF에서는 펼쳐 전체 내용을 포함한다. 참고 링크는 PDF에서도 확인할 수 있게 한다.
6. `application/pdf`와 첨부 파일 헤더를 반환한다. 예시 파일명은 `TrendWeave_UNIQLO_2027_SS_<report_id>.pdf`다.
7. PDF 생성 실패는 보고서 분석 완료 상태를 바꾸지 않는다. 다시 분석하지 않고 다운로드만 재시도할 수 있게 한다. PDF 생성 중 버튼 상태도 별도로 관리한다.

브라우저의 인쇄 기능은 개발 중 레이아웃 확인에 사용할 수 있지만, 최종 완료 기준은 다운로드 버튼으로 실제 PDF 파일을 받는 것이다. 외부 검색 결과의 HTML이나 원격 자원을 PDF 엔진에 그대로 넘기지 않고 정제된 보고서와 로컬 자원을 사용한다.

## 7. 제안 파일 구조

```text
agent/trendweave/
  schemas.py          # RequestProfile, AxisResult, 보고서·Critic 스키마
  state.py            # 상위 및 Research State, Reducer
  config.py           # 축 설정, 프롬프트 설정, 루프 상한
  deps.py             # 모델·검색 도구·공유 제한기 생성
  search.py           # Tavily 호출, 검색어 및 문서 유틸리티
  research.py         # Search/Grade/Rewrite/Extract와 서브그래프
  strategy.py         # Planner, Writer, Critic, 규칙 검사
  report.py           # 최종 Markdown 및 참고문헌 조립
  graph.py            # 전체 그래프와 실행 진입점
services/
  report_service.py   # 작업 실행·상태·이벤트 전달
  report_store.py     # SQLite 보고서·작업·이벤트 저장
  pdf_service.py      # Markdown → HTML → PDF
templates/
  report_pdf.html     # PDF 템플릿 및 인쇄 스타일
static/fonts/         # 배포 가능한 한국어 글꼴
tests/                # 핵심 규칙·API·PDF 검증
```

기존 파일 중 `server.py`, `web_demo_server.py`, `web_chat.html`, `requirements.txt`, `.env.example`, `run.sh`, `README.md`를 수정할 예정이다. 기존 장애 대응 그래프와 패션 그래프는 분리하여 구현하고, 패션 분석이 기존 MCP 초기화 성공 여부에 불필요하게 종속되지 않도록 서비스 초기화를 구성한다.

## 8. 단계별 실행 계획과 완료 조건

| 단계 | 구현 내용 | 완료 조건 |
|---|---|---|
| 1. 환경·동작 확인 | 노트북 의존성 추출, 모델·검색 키 및 모델 지원 확인, PDF 도구·한국어 출력 사전 검증 | 모델 구조화 출력 1회, Tavily 검색 1회, 한국어 샘플 PDF 생성 성공 |
| 2. 분석 코드 모듈화 | 스키마·State·검색 유틸리티·Research·Strategy·Critic·Report·전체 그래프 이식 | UI 없이 분석 함수로 4축 보고서 생성. 기본 요청과 데님 요청의 계획 차이 확인 |
| 3. FastAPI 연결 | 작업 저장·백그라운드 실행·상태 조회·SSE·프록시 구현 | POST 후 상태가 완료/실패로 수렴하고, 완료 보고서를 ID로 재조회 가능 |
| 4. 채팅 화면 연결 | 서비스명·안내 문구, 시즌 입력, 예시 질문 버튼, 진행 단계, 보고서 미리보기 구현 | 예시 버튼 한 번으로 실제 보고서 생성·표시. 중복 클릭과 연결 오류 복구 확인 |
| 5. PDF 연결 | 저장 결과 변환, 한국어 글꼴, 인쇄 스타일, 바이너리 프록시, 다운로드 UI | 긴 보고서가 한국어·표·링크·검토 기록을 유지한 PDF로 다운로드됨 |
| 6. 통합 검증·발표 자료 | 기본·변형·실패 시나리오, 실행 안내와 한계 정리 | 질문 → 분석 → 웹 표시 → PDF의 실제 시연 자료 확보 |

환경 및 PDF 샘플 검증을 먼저 하여 설치 문제를 조기에 확인하되, 본 구현은 **분석 함수 → API → 예시 버튼 → PDF → 통합 검증** 순서로 진행한다. 제출 시간이 제한되면 디자인 변경보다 이 흐름의 완성과 검증을 우선한다.

## 9. 검증 계획

외부 호출 없는 규칙·API 테스트를 먼저 수행하고, 실제 API를 사용하는 통합 실행은 대표 입력 위주로 제한한다. 테스트용 대체 결과와 실제 웹 검색 결과를 구별한다.

| 시나리오 | 확인할 내용 |
|---|---|
| 기본 예시 질문 | 4축 결과, 전략 3개, 출처·품질·검토·Trace 섹션 생성 |
| 데님 중심 요청 | 기본 요청과 다른 요청 프로필·검색 초점이 생성되고 결과에 조건이 반영됨 |
| 먼 미래 시즌·자료 부족 | 검색 총 3회 이내 종료, 낮은 신뢰도와 누락 측면 표시 |
| 다른 시즌·쇼핑몰 문서 | Grade가 노트북 기준에 따라 자료를 탈락시킴 |
| 존재하지 않는 근거·근거 없는 컬러 | 규칙 또는 Critic이 문제를 발견하고 재작성 상한을 지킴 |
| Color Signal 없음 | 컬러를 생략한 방향에 잘못된 컬러 필수 오류를 반복하지 않음 |
| 한 축 실패·전체 검색 실패 | 부분 결과와 전체 실패 상태를 구분하고 실패 원인이 남음 |
| 키 누락·429·timeout | 무한 재시도 없이 종료하거나 안내하며 UI 실행 상태가 해제됨 |
| 중복 클릭·SSE 재연결 | 하나의 클릭 흐름에서 작업이 중복 생성되지 않고 기존 작업 구독이 이어짐 |
| 동시 요청·서버 재시작 | 보고서·이벤트가 섞이지 않고 완료 결과가 보존되며 중단 작업 상태가 정리됨 |
| 긴 한글 PDF | 한글 깨짐·내용 잘림·표 넘침 없음. 전체 섹션과 References, 펼친 Trace 포함 |
| PDF 생성 실패 | 보고서 조회는 유지되고 PDF만 재시도 가능 |
| Markdown 입력 | 스크립트가 실행되지 않고 외부 자료가 안전하게 표시됨 |

기록할 항목은 실행 입력, 모델 설정, 소요 시간, 검색·재작성 횟수, 축별 신뢰도, 남은 검토 문제, 성공/실패 원인이다. PDF는 파일 생성 여부뿐 아니라 실제 페이지를 열어 육안으로도 확인한다.

## 10. 범위와 최종 산출물

1차 완료 기준:

- 예시 질문 버튼 한 번으로 UNIQLO 4축 실제 분석이 시작된다.
- 진행 상태와 오류가 화면에 표시되고, 긴 보고서를 읽기 좋은 형태로 확인할 수 있다.
- 화면에 표시된 동일 보고서를 PDF 파일로 다운로드할 수 있다.
- 노트북의 재검색·근거 연결·Critic 재작성·한계 표시가 유지된다.
- `.env.example`과 README만으로 필요한 설정과 실행 방법을 파악할 수 있다.
- 기본/변형 입력, 실패 처리, PDF 검증 결과와 발표용 화면을 남긴다.

2차 확장 범위:

- 질문 분류에 따른 선택적 분석 축 실행과 보고서 형식 변경
- 코디 추천, 브랜드 확장, 이전 보고서에 대한 문맥 기반 후속 대화
- 내부 판매·재고 데이터, 런웨이 이미지 분석, 평가 지표 고도화
- 사용자별 보고서 목록, 인증, 다중 워커 작업 큐와 자동 작업 복구

기본 4축 상품기획 보고서와 PDF 다운로드를 완성한 뒤, 질문별 분석 축 선택을 별도 단계로 확장한다.

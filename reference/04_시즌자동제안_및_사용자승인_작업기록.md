# 4번 작업: 요청 시점 기반 시즌 자동 제안과 사용자 승인

작성일: 2026-10-21
브랜치: `feature/trendweave-reports`

## 구현한 서비스 흐름

사용자가 질문을 보내면 바로 보고서를 만들던 흐름을 다음과 같이 변경했다.

```text
질문 입력 또는 예시 질문
  → 서버가 요청 시각을 한국시간으로 기록
  → LLM이 시즌·ZARA 기반 보고서 방향·이유를 제안
  → 사용자가 시즌·브랜드·요청·방향을 검토하고 필요한 값 수정
      ├─ 생성 취소: 보고서 작업을 생성하지 않음
      └─ 확인하고 보고서 생성: 승인한 내용으로 기존 4축 분석 실행
          → 누적 진행 기록 → 보고서 → PDF
```

브랜드는 앞선 사용자 요청대로 **ZARA 고정**을 유지한다. 확인 카드에서 브랜드를 검토할 수 있지만 다른 브랜드를 선택하는 확장 기능은 추가하지 않았다. 일반 질문 분류, 질문별 분석 축 선택, 이전 대화 맥락 분석도 추가하지 않았다.

## 1. LLM 시즌 판단

`agent/trendweave/review.py`에 `PlanningSuggestion` 구조화 출력과 제안 프롬프트를 정의했다. 기존 Gemini 모델과 공용 속도 제한기를 재사용한다.

- 요청 기준 시각은 클라이언트 값이 아니라 서버의 `Asia/Seoul` 시각이다.
- 사용자가 연도·시즌을 명시하면 이를 우선하고, 계절만 언급하면 요청 시점과 상품기획 맥락으로 연도를 제안한다.
- 시즌이 없으면 지금 준비할 다음 상품기획 시즌을 LLM이 제안한다. `2027 S/S` 같은 고정 기본값이나 월별 코드 규칙으로 시즌을 결정하지 않는다.
- 모호한 요청에는 가정을 이유로 설명한다. 사용자는 이를 확인한 뒤 수정할 수 있다.
- 시즌 형식과 ZARA 브랜드, 비어 있지 않은 방향·이유는 Pydantic으로 검증한다.
- 제안 단계에서는 검색과 보고서 생성을 수행하지 않는다. LLM 실패 시 임의 시즌으로 분석을 시작하지 않고 재시도를 안내한다.

## 2. 사용자가 검토하는 카드

기존 입력창의 시즌 선택을 제거하고, 질문 전송 후 대화 안에 별도의 확인 카드를 표시한다.

카드 내용:

- 서버에 기록된 요청 기준 시각(한국시간)
- LLM이 제안한 원래 시즌과 판단 이유
- 수정 가능한 분석 시즌
- 읽기 전용 분석 브랜드 ZARA
- 수정 가능한 원래 상품기획 요청
- 수정 가능한 보고서 방향
- **확인하고 보고서 생성**, **생성 취소** 버튼

원래 LLM 제안 시즌은 별도로 유지하므로 사용자가 시즌을 수정한 뒤에도 이유가 어떤 제안에 대한 설명이었는지 확인할 수 있다. 시즌 입력칸의 Enter만으로 자동 승인하지 않고, 승인 버튼 클릭 또는 버튼의 키보드 조작으로 진행한다.

제안이 준비되면 확인 카드의 앞부분을 읽을 수 있도록 위치와 포커스를 조정한다. 이전 대화를 읽고 있으면 강제로 화면을 이동시키지 않는다. 확인 대기 중에도 다음 요청의 초안을 작성할 수 있지만, 먼저 현재 제안을 승인하거나 취소해야 새 제안을 요청할 수 있다.

승인·취소 결과는 대화 내역에 남는다. 새로고침하면 1번 작업에서 정한 대로 제안 카드와 대화도 초기화하며, 미승인 제안은 자동 실행하지 않는다.

## 3. 서버 승인 경계와 저장

API를 다음과 같이 분리했다.

| API | 동작 |
|---|---|
| `POST /reports/preview` | 요청 시각을 기록하고 LLM 제안을 저장·반환. 보고서 생성 없음 |
| `POST /reports` | 기존 제안 ID와 `approved=true`, 검토한 값이 있어야 분석 작업 생성 |
| `POST /reports/preview/{preview_id}/cancel` | 해당 대화의 제안을 취소하여 이후 승인 방지 |
| 기존 GET 조회·SSE·PDF | 승인 후 생성된 보고서에 기존 방식 그대로 적용 |

`report_previews` 테이블을 서버 시작 시 자동 생성한다. 제안 원문·시각·대화 ID·대기/승인/취소 상태·승인한 수정 내용·연결 보고서 ID를 저장한다. 기존 보고서와 이벤트 테이블은 유지한다.

- 제안이 없거나 다른 대화의 제안이면 생성하지 않는다.
- `approved=true`가 없거나 ZARA 외 브랜드·잘못된 시즌·빈 방향이면 입력 오류로 처리한다.
- 취소한 제안은 승인할 수 없다.
- 같은 승인 요청이 재전송되면 이미 생성한 동일 보고서 ID를 반환한다. 새로운 작업을 중복 생성하지 않는다.
- 이미 승인한 제안을 다른 내용으로 다시 실행하려 하면 새 질문으로 확인하도록 안내한다.
- 승인 처리와 작업 삽입은 잠금 및 같은 SQLite 트랜잭션 안에서 수행한다.
- 작업 대기 한도가 찼으면 제안을 승인 대기 상태로 유지하여 다시 시도할 수 있게 한다.

`services/report_service.py`에서 사용자가 확인한 보고서 방향을 분석 요청에 함께 넣는다. 화면에서만 수정되고 실제 Planner에 전달되지 않는 상황을 방지했다. 승인 후에는 기존 4축 조사·재검색·Critic·보고서·PDF 흐름을 그대로 사용한다.

## 5. 검증 결과

### 자동 테스트

```bash
.venv/bin/python -m pytest -q --tb=short
```

결과: **34 passed**. JavaScript 구문 검사, Python 컴파일과 `git diff --check`도 통과했다.

주요 확인 사항:

1. 서버 요청 시각과 원래 질문이 LLM 입력에 전달됨
2. 제안 시 보고서 작업이 생성되지 않음
3. 누락·거절 승인, 존재하지 않는 제안, 다른 대화, 취소된 제안은 실행 불가
4. 사용자가 수정한 시즌·요청·방향이 저장되고 방향이 실제 분석 입력에 반영됨
5. 중복 승인 시 같은 작업 ID 반환, 이미 승인한 내용의 변경 방지
6. 취소·LLM 제안 실패 시 보고서가 생성되지 않음
7. 대기 한도 초과 시 제안이 승인 대기 상태로 유지됨
8. 제안 감사 정보가 서버 재시작 후에도 보존됨
9. 데스크톱·모바일에서 승인 전 실제 생성 요청이 전송되지 않음
10. 확인 카드의 읽기 전용 ZARA·수정 입력·취소·중복 클릭 방지·오류 후 수정 내용 유지
11. 시즌 입력 Enter만으로 승인하지 않음
12. 기존 새로고침 초기화·연속 대화·누적 기록·보고서·PDF 동작 유지

브라우저 테스트는 실제 HTML·Vue·JavaScript·CSS와 테스트 API 응답을 사용했으며 외부 API를 호출하지 않았다. 1280×900, 390×844 확인 카드 스크린샷을 직접 확인했다. 브라우저 오류나 가로 넘침은 없었다.

## 6. 실행과 사용자 확인

백엔드·프록시·DB 초기화 코드가 변경되었으므로 실행 중인 터미널에서 `Control + C`로 종료하고 다시 실행한다.

```bash
./run.sh
```

1. `http://localhost:8600`을 새로고침한다.
2. 예시 질문 또는 시즌을 명시하지 않은 상품기획 요청을 전송한다.
3. 확인 카드에서 요청 시각, 시즌 제안과 이유, ZARA 및 보고서 방향을 검토한다.
4. 필요하면 시즌·요청·방향을 수정한다.
5. 취소하면 보고서 카드가 생성되지 않는지 확인한다.
6. 새 요청을 보내고 **확인하고 보고서 생성**을 누르면 누적 분석 기록과 보고서가 생성되는지 확인한다.

ZARA 고정 및 4축 보고서 형식은 유지하며, 1~4번으로 요청한 개선 작업은 모두 구현했다. 추가 작업은 사용자 확인 후 진행한다.
